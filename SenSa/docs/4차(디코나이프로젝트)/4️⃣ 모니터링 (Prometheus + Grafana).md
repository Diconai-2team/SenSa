작업 목적

2단계에서는 시스템이 단순히 동작하는 수준을 넘어,  
**어디가 느린지, 어디서 오류가 발생하는지, 어떤 구간이 병목인지**를 운영자가 수치로 확인할 수 있어야 한다.  
이를 위해 Django, FastAPI, Celery, Redis, DB 등 주요 구성요소의 상태를 메트릭으로 수집하고,  
Grafana 대시보드에서 시각화하여 **운영 가능한 관제 플랫폼**으로 고도화하는 것이 목적이다.

1단계에서 “보이게 만드는 것”이 목표였다면,  
2단계에서는 “제대로 돌아가고 있는지 관찰할 수 있는 것”이 목표다.  
특히 본 프로젝트는 실시간 데이터 처리, AI 이상 탐지, 알람 생성, 비동기 작업, 지오펜스 판단이 모두 연결되어 있으므로  
성능 문제나 장애가 발생했을 때 **정확히 어느 구간에서 병목이 생겼는지** 추적할 수 있어야 한다.

---
작업 내용

1. 모니터링 대상 시스템 정의
- 모니터링은 서버 한 대만 보는 것이 아니라, 프로젝트의 주요 구성요소 전체를 대상으로 해야 한다.
- 우선순위 대상은 다음과 같다.
    - Django 관제 서버
    - FastAPI 엣지/AI 서버
    - Celery Worker
    - Redis
    - PostgreSQL
- 2단계 초기에는 Django와 FastAPI부터 시작하고, 이후 Celery와 Redis/DB까지 확장하는 방식이 적절하다.

2. Django 메트릭 수집
- Django는 관제 시스템의 핵심 백엔드이므로,  
    API 요청 처리 상태와 내부 핵심 로직의 수행 시간을 확인할 수 있어야 한다.
- 기본적으로 수집할 항목:
    - API 요청 수
    - API 응답 시간
    - 상태 코드별 응답 수
    - 에러율
- 프로젝트 특화 커스텀 메트릭:
    - 지오펜스 판단 시간
    - 알람 발생 횟수
    - 이벤트 생성 횟수
    - AI 분석 요청 횟수
- 이를 통해 “느린 API”, “자주 실패하는 기능”, “알람이 얼마나 자주 발생하는지”를 한눈에 볼 수 있다.

3. FastAPI 메트릭 수집
- FastAPI는 센서 데이터 수집, 실시간 송신, AI 분석 등  
    실시간성과 계산량이 높은 역할을 담당하므로 별도 모니터링이 매우 중요하다.
- 기본적으로 수집할 항목:
    - 요청 수
    - 응답 시간
    - 에러율
- 프로젝트 특화 항목:
    - WebSocket 연결 수
    - 센서 데이터 처리 속도
    - AI 분석 수행 시간
    - AI 분석 실패 수
- 특히 AI 서버는 “응답이 느려졌는지”, “분석 시간이 얼마인지”, “오류가 어디서 나는지”를 봐야 하므로  
    커스텀 메트릭 설계가 중요하다.

4. Celery 메트릭 수집
- 비동기 작업이 도입되면 API는 빨라질 수 있지만,  
    뒤에서 처리하는 작업이 밀리면 실제 시스템은 느려질 수 있다.
- 따라서 Celery는 단순히 “돌아가고 있다”가 아니라,  
    **작업이 얼마나 쌓이고 있는지, 얼마나 실패하는지, 얼마나 오래 걸리는지**를 봐야 한다.
- 주요 항목:
    - task 처리 시간
    - task 성공/실패 횟수
    - 큐 적체 상태
    - 재시도 횟수
- AI 분석이 Celery task로 분리된 경우, AI 처리 지연을 정확히 확인하는 핵심 포인트가 된다.

5. Redis / PostgreSQL 메트릭 수집
- Redis와 DB는 시스템의 기초 인프라이므로,  
    장애나 지연이 생기면 전체 구조가 영향을 받는다.
- Redis:
    - 연결 상태
    - 메모리 사용량
    - Pub/Sub 처리량
    - queue/backlog 상태
- PostgreSQL:
    - 연결 수
    - 쿼리 처리 시간
    - 느린 쿼리 여부
    - DB 부하 상태
- 2단계 초반에는 상세 쿼리 분석까지 안 가더라도  
    지금 Redis/DB가 병목 원인인지 아닌지 정도는 판별 가능해야 한다.

6. Prometheus 수집 구조 구성
- Prometheus는 각 서버의 `/metrics` 엔드포인트를 주기적으로 수집(scrape)한다.
- 예:
    - Django: `/metrics`
    - FastAPI: `/metrics`
- Celery, Redis, DB는 Exporter 또는 통합 메트릭 방식으로 수집 가능하다.
- 수집 주기와 타깃을 명확히 정의해야 하며,  
    로컬 Docker 환경에서는 서비스명 기반으로 타깃을 설정한다.
- 즉, Prometheus는 **“전체 시스템 상태를 한곳으로 모으는 수집기”** 역할을 한다.

7. Grafana 대시보드 구성
- Grafana는 Prometheus에 쌓인 메트릭을 시각화한다.
- 2단계에서는 단순한 예쁜 그래프보다  
    운영자가 실제로 봐야 할 질문에 답하는 대시보드를 구성해야 한다.

주요 질문 예시:
- 현재 요청이 얼마나 들어오고 있는가?
- 응답 시간이 느려지고 있는가?
- 에러가 증가하고 있는가?
- AI 분석이 병목인가?
- Celery 작업이 밀리고 있는가?
- 알람이 과도하게 발생하고 있는가?
- 이를 기반으로 패널을 구성한다.

8. 핵심 대시보드 항목 정의
	2단계 우선 패널 예시:

Django
- API 요청 수 (RPS)
- 평균 응답 시간
- p95 응답 시간
- 에러율
- 알람 발생 횟수
- 지오펜스 판단 시간

FastAPI
- 요청 수
- 평균 응답 시간
- p95 응답 시간
- WebSocket 연결 수
- AI 분석 시간
- AI 실패 횟수

Celery
- task 성공 수
- task 실패 수
- 평균 처리 시간
- 큐 적체 상태

Redis / DB
- 연결 상태
- 응답 지연
- 처리량
- 초기에는 너무 많은 패널을 만들기보다  
    “병목 확인에 직접 도움이 되는 핵심 패널”부터 우선 만든다.

9. 커스텀 메트릭 설계
- 기본 메트릭만으로는 프로젝트 특화 병목을 파악하기 어렵다.
- 이 프로젝트는 특히 다음과 같은 커스텀 메트릭이 중요하다.
    - 지오펜스 판단 시간
    - AI 요청 수
    - AI 분석 시간
    - 위험 이벤트 발생 수
    - 알람 전송 횟수
    - Celery task별 처리 시간
- 예를 들어 응답이 느릴 때  
    “DB 저장 때문인지, AI 서버 때문인지, 지오펜스 판별 때문인지”를 알 수 있어야 하므로  
    핵심 구간별 시간을 별도로 측정하는 것이 좋다.

10. 병목 분석 관점 적용
- 모니터링의 목적은 단순히 그래프를 띄우는 것이 아니라  
    **문제가 어디에 있는지 해석할 수 있게 하는 것**이다.
- 예:
    - Django 응답 시간 증가 + FastAPI 정상 → Django 내부 병목 가능성
    - AI 처리 시간 급증 + Celery 적체 증가 → AI 분석 병목 가능성
    - Redis 지연 증가 + WebSocket 끊김 증가 → Redis 병목 가능성
- 즉, 각 서비스의 메트릭을 따로 보는 것이 아니라  
    서로 연결해서 읽을 수 있어야 한다.

11. 테스트와 부하 시나리오 연결
- 모니터링은 실제 부하 없이 보면 의미가 약하다.
- 따라서 다음 같은 테스트와 함께 확인해야 한다.
    - 센서 데이터 송신 주기 증가
    - 작업자 수 증가
    - AI 분석 요청 증가
    - 이벤트/알람 연속 발생
- 이때 Grafana에서 어떤 패널이 먼저 튀는지를 확인하면  
    시스템 한계와 병목 구간을 찾을 수 있다.

12. 운영 관점 경보 준비
- 2단계 후반에는 단순 시각화뿐 아니라  
    특정 조건에서 운영자에게 자동 경고를 줄 수 있어야 한다.
- 예:
    - AI 분석 시간이 일정 기준 초과
    - 에러율 급증
    - Celery task 실패 누적
    - Redis 응답 지연 증가
- 초기에는 Grafana에서 수동 확인 중심으로 가고,  
    이후 Alertmanager 또는 외부 알림 채널과 연계할 수 있도록 확장 구조를 준비한다.

세부 작업 순서

STEP 1. 모니터링 우선 대상 확정
- Django, FastAPI를 1순위로 잡고,  
    이후 Celery, Redis, PostgreSQL 순으로 확장 계획을 정한다.

STEP 2. Django 메트릭 노출
- Django에 Prometheus 연동을 추가하고 `/metrics` 엔드포인트를 확인한다.
- 기본 요청/응답 메트릭이 정상적으로 노출되는지 검증한다.

STEP 3. FastAPI 메트릭 노출
- FastAPI에 메트릭 수집 라이브러리를 붙이고 `/metrics` 노출을 확인한다.
- 기본 HTTP 메트릭과 프로젝트 특화 메트릭 구조를 준비한다.

STEP 4. 커스텀 메트릭 추가
- 지오펜스 판단 시간, AI 분석 시간, 알람 발생 횟수 등  
    핵심 구간의 custom counter / histogram을 추가한다.

STEP 5. Prometheus 설정
- `prometheus.yml`에 Django, FastAPI, Exporter 타깃을 등록한다.
- Docker Compose 환경에서 서비스명 기준으로 scrape가 가능한지 점검한다.

STEP 6. Grafana 연결
- Prometheus를 데이터 소스로 등록한다.
- 기본 대시보드와 커스텀 패널을 생성한다.

STEP 7. 핵심 패널 구성
- 요청 수, 응답 시간, 에러율, AI 처리 시간, Celery 처리 시간, Redis 상태 등을 패널로 만든다.

STEP 8. 부하 테스트 연동
- 실시간 데이터 송신, 이벤트 연속 발생, AI 요청 증가 상황을 만들고  
    Grafana 패널이 어떻게 반응하는지 확인한다.

STEP 9. 병목 해석 문서화
- 어떤 패널이 어떤 문제를 의미하는지 간단한 해석 가이드를 정리한다.

STEP 10. 경보 기준 초안 마련
- 응답 시간, 실패율, AI 처리 시간 등에 대해 운영 기준 임계값을 초안 형태로 정리한다.

- 운영자가 수동으로라도 현재 시스템 상태를 판단할 수 있다.

작업 시 주의사항

- 모니터링은 “보여주기용 그래프”가 아니라  
    실제 문제 원인을 찾기 위한 도구로 설계해야 한다.
- 기본 메트릭만 보면 서비스 특화 병목을 놓칠 수 있으므로  
    지오펜스, AI, 알람 등 핵심 업무 로직에는 커스텀 메트릭이 필요하다.
- 처음부터 모든 메트릭을 다 붙이기보다  
    운영 의사결정에 필요한 핵심 지표부터 우선 수집하는 것이 현실적이다.
- p95 같은 고분위 응답 시간은 평균보다 실제 사용자 체감 병목을 더 잘 보여줄 수 있다.
- Celery와 Redis를 도입한 이후에는  
    “API는 빠른데 실제 처리는 밀리는” 상황이 생길 수 있으므로  
    웹 응답 메트릭만 보지 말고 백그라운드 작업 메트릭도 함께 봐야 한다.
- 본 프로젝트는 실시간 모니터링, AI 분석, 경보 및 대응 연계, API 연계 현황 관리, 시스템 로그 관리까지 요구사항에 포함되므로,  
    모니터링은 부가 기능이 아니라 운영 단계 진입을 위한 핵심 기반이다.
