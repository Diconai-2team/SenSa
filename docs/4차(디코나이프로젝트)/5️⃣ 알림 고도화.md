작업 목적

1단계에서는 관제 화면 내부에서 위험 이벤트를 시각적으로 보여주는 알람 UI를 구현했다면,  
2단계에서는 위험 상황이 발생했을 때 운영자가 화면을 보고 있지 않더라도 즉시 인지할 수 있도록  
실시간 화면 알림 + 외부 채널 알림 체계를 함께 구성하는 것이 목적이다.

즉, 알림 고도화의 핵심은  
단순히 화면에 경고를 띄우는 수준을 넘어,  
위험 이벤트가 발생했을 때

- 관제 화면 내 즉시 반영
- 운영자 외부 협업 채널 전송
- 알림 이력 추적  
    까지 연결되는 **실운영형 알림 체계**를 만드는 것이다.

이 기능은 요구사항 문서의
- 경보 및 대응 연계
- 경보 발생 조건 설정
- 경보 이력 관리
- 외부/내부 시스템 연계 현황 관리  
    와도 직접 연결되는 운영 핵심 기능이다.

---
작업 내용

1. 알림 채널 구조 분리
- 알림은 하나의 방식으로만 처리하지 않고, **내부 알림**과 **외부 알림**으로 구분한다.
- 내부 알림:
    - WebSocket 기반 관제 화면 실시간 알람
    - 경고 배너, 이벤트 리스트, 지도 강조
- 외부 알림:
    - Slack
    - Discord
    - (향후 확장) 이메일, 문자, 사내 메신저
- 이렇게 분리하면 화면 운영과 외부 대응 체계를 동시에 확보할 수 있다.

2. 알림 발생 기준 정리
- 모든 이벤트를 외부 채널로 보내면 운영자가 피로감을 느낄 수 있으므로  
    어떤 이벤트를 어떤 채널로 보낼지 기준을 정해야 한다.
- 예:
    - 정상 상태: 외부 알림 없음
    - 주의 상태: 화면 표시만
    - 위험 상태: 화면 + 외부 채널 전송
    - AI 예측 위험: 조건부 외부 알림
- 즉, 알림은 “발생 여부”뿐 아니라 “중요도에 따라 채널을 다르게 쓰는 구조”로 설계한다.

3. WebSocket 기반 내부 알림 강화
- 서버에서 생성한 알람 이벤트를 WebSocket으로 브라우저에 전달하여  
    화면이 즉시 갱신되도록 한다.
- 2단계에서는 1단계보다 더 정교하게 다음을 반영할 수 있다.
    - 신규 알람 강조
    - 심각도별 다른 애니메이션 또는 배너 스타일
    - 미확인 알람 수 표시
    - 최근 알람 누적
- 즉, 내부 알림은 단순 메시지 출력이 아니라  
    운영자가 “현재 얼마나 위험한 상태인지” 즉시 파악할 수 있는 대시보드 요소로 발전해야 한다.

4. 외부 알림 채널 연동
- Slack 또는 Discord Webhook을 사용하여  
    위험 이벤트 발생 시 외부 채널에 자동 메시지를 전송한다.
- 2단계에서는 구현 난이도와 시연 편의성을 고려하면  
    Discord Webhook 또는 Slack Incoming Webhook 방식이 가장 적절하다.
- Webhook 기반 알림은 서버에서 HTTP 요청만 보내면 되므로  
    구조가 단순하고 관제 시스템과 쉽게 연결된다.

5. 알림 메시지 포맷 정의
- 외부 알림은 짧고 명확해야 하며, 운영자가 한눈에 이해할 수 있도록 구조화해야 한다.
- 최소 포함 정보:
    - 발생 시각
    - 위험 레벨
    - 작업자명 또는 대상
    - 센서명
    - 지오펜스명
    - 측정값
    - 메시지 요약
- 예:
    - `[위험] 10:01 작업자 A / 위험구역 A / CO=230ppm / 즉시 확인 필요`
- 가능하면 메시지 형식을 통일해 운영자가 알림만 보고도 상황을 해석할 수 있도록 한다.

6. 이벤트 종류별 알림 분기
- 모든 알림이 동일한 메시지 형식을 가질 필요는 없다.
- 예:
    - 가스 위험 알림
    - 전력 이상 알림
    - 지오펜스 진입 경고
    - AI 예측 경고
    - 시스템 장애 알림
- 이벤트 유형에 따라 메시지 제목, 아이콘, 색상, 전송 채널을 다르게 구성할 수 있다.
- 이렇게 하면 운영자가 어떤 종류의 문제인지 빠르게 이해할 수 있다.

7. 알림 전송 시점과 비동기 처리
- 외부 알림 전송은 네트워크 요청이 포함되므로  
    메인 응답 흐름에서 직접 처리하지 않고 비동기 task(Celery)로 넘기는 것이 적절하다.
- 권장 흐름:
    1. 서버에서 위험 이벤트 생성
    2. 내부 WebSocket 알림 즉시 송신
    3. 외부 채널 전송 task 등록
    4. Celery가 Slack/Discord로 비동기 전송
- 이렇게 하면 화면 알림은 빠르게 유지하고,  
    외부 채널 전송 실패가 메인 시스템 응답에 영향을 주지 않게 할 수 있다.

8. 알림 이력 저장
- 외부 채널에 전송한 알림도 이벤트 이력으로 관리해야 한다.
- 저장 항목 예시:
    - alert_id
    - event_id
    - channel_type (websocket / slack / discord)
    - sent_at
    - send_status (success / fail)
    - fail_reason
- 이력 저장을 해두면
    - 실제 전송 여부 확인
    - 실패 원인 분석
    - 운영 로그 관리  
        가 가능하다.

9. 중복 알림 방지 및 묶음 처리
- 동일한 위험 이벤트가 연속 발생할 경우  
    외부 채널이 도배되면 오히려 실운영에서 불편하다.
- 따라서 중복 알림 방지 정책이 필요하다.
- 예:
    - 동일 작업자 + 동일 센서 + 동일 구역 + 동일 위험 단계는 1분 내 1회만 전송
    - 같은 이벤트가 지속되면 “지속 중” 상태로 묶음 처리
    - 위험 단계가 상승할 때만 재전송
- 내부 UI와 외부 채널은 중복 제어 강도를 다르게 둘 수 있다.

10. 수신 대상과 운영 정책 분리
- 실제 운영에서는 모든 사람이 모든 알림을 받을 필요는 없다.
- 초기 단계에서는 단일 운영 채널로 보내더라도,  
    향후에는 다음처럼 분리할 수 있어야 한다.
    - 안전 담당자 채널
    - 시스템 운영 채널
    - 관리자 전용 채널
- 즉, 알림 시스템은 단순 전송이 아니라  
    “누가 무엇을 받아야 하는가”까지 확장 가능한 구조를 가져야 한다.

11. 장애/실패 알림 추가 고려
- 운영 환경에서는 위험 이벤트뿐 아니라 시스템 자체의 이상도 알려야 한다.
- 예:
    - AI 서버 응답 실패
    - WebSocket 끊김 증가
    - Celery 작업 실패 누적
    - Redis 지연 증가
- 이 항목은 모니터링과 연결되며,  
    향후 Prometheus Alertmanager와 연계하여 시스템 경보로 확장할 수 있다.
- 2단계 초반에는 업무 이벤트 알림부터 구현하고, 이후 시스템 장애 알림으로 넓히는 것이 적절하다.

12. 운영자 대응 흐름 연결
- 알림이 발생했을 때 운영자가 무엇을 해야 하는지 화면과 외부 채널에서 유추 가능해야 한다.
- 예:
    - “즉시 확인 필요”
    - “작업자 대피 필요”
    - “설비 점검 필요”
- 단순 수치만 보내기보다 행동 유도형 메시지를 포함하면 실무 활용성이 훨씬 높아진다.

세부 작업 순서

STEP 1. 알림 채널 분류
- 내부 알림(WebSocket)과 외부 알림(Slack/Discord)을 분리 정의한다.
- 어떤 위험 수준에서 어떤 채널을 사용할지 기준을 정한다.

STEP 2. 알림 메시지 포맷 설계
- 가스 위험, 전력 이상, AI 예측, 시스템 장애 등 이벤트 유형별 메시지 형식을 정한다.

STEP 3. WebSocket 내부 알림 고도화
- 기존 알람 UI에 미확인 상태, 신규 강조, 누적 표시 등을 반영한다.

STEP 4. 외부 Webhook 연동
- Slack 또는 Discord Webhook URL을 준비하고, 테스트 메시지를 전송한다.

STEP 5. 서버 알림 전송 모듈 구현
- 위험 이벤트 발생 시 외부 전송용 메시지를 생성하는 로직을 작성한다.

STEP 6. Celery 비동기 분리
- 외부 채널 전송은 Celery task로 분리하여 처리한다.

STEP 7. 알림 이력 저장
- 전송 성공/실패 여부와 전송 시각을 DB 또는 로그에 저장한다.

STEP 8. 중복 알림 방지 정책 적용
- 동일 이벤트 반복 전송을 제한하는 규칙을 적용한다.

STEP 9. 테스트 시나리오 검증
- 정상 이벤트, 반복 위험 이벤트, 전송 실패, 재시도, 다중 이벤트 발생 상황을 점검한다.

STEP 10. 운영 정책 문서화
- 어떤 이벤트가 어떤 채널로 가는지, 누가 받는지, 재전송 기준은 무엇인지 정리한다.

---
권장 처리 흐름

① 위험 이벤트 생성  
② 내부 WebSocket 알림 즉시 송신  
③ 외부 알림 전송 task 등록  
④ Celery Worker가 Slack/Discord 전송  
⑤ 전송 결과 저장  
⑥ 필요 시 UI/이력 화면 반영

예시 구조

내부 알림 흐름
```
위험 판단 로직  
   ↓  
WebSocket 메시지 생성  
   ↓  
브라우저 수신  
   ↓  
경고 배너 / 이벤트 리스트 / 지도 강조
```

외부 알림 흐름
```
위험 판단 로직  
   ↓  
Celery task 등록  
   ↓  
Slack / Discord Webhook 전송  
   ↓  
전송 결과 저장
```

알림 메시지 예시

WebSocket 내부 알림 예시
```json
{  
  "type": "alert",  
  "timestamp": "2026-04-12T10:01:10",  
  "level": "danger",  
  "worker_name": "작업자 A",  
  "sensor_name": "가스센서 A",  
  "geofence_name": "위험구역 A",  
  "message": "작업자 A가 위험구역 A 내부에서 CO 위험 수치에 노출됨"  
}
```

Discord/Slack 전송 메시지 예시
```json
{  
  "text": "[위험] 10:01 작업자 A / 위험구역 A / 가스센서 A / CO=230ppm / 즉시 확인 필요"  
}
```

---
완료 기준

- 위험 이벤트가 발생하면 관제 화면에 WebSocket으로 즉시 반영된다.
- 위험 수준에 따라 외부 알림 채널(Slack/Discord)로 메시지가 전송된다.
- 내부 알림과 외부 알림이 서로 다른 목적에 맞게 동작한다.
- 외부 전송이 메인 API 응답을 지연시키지 않는다.
- 알림 메시지 형식이 통일되어 운영자가 빠르게 해석할 수 있다.
- 동일 이벤트 반복 시 외부 채널이 과도하게 중복되지 않는다.
- 전송 성공/실패 여부가 기록된다.
- 운영자가 알림 이력과 전송 상태를 추적할 수 있다.

작업 시 주의사항

- 알림은 많이 보내는 것보다 **정확하고 필요한 것만 보내는 것**이 더 중요하다.
- 내부 알림과 외부 알림의 역할을 명확히 나누지 않으면 운영자가 혼란을 겪을 수 있다.
- 외부 채널은 네트워크 의존성이 있으므로 반드시 비동기 처리하는 것이 좋다.
- 동일 이벤트 반복 전송은 운영 피로도를 크게 높이므로 중복 방지 정책이 필수다.
- 알림 메시지는 기술자만 이해할 수 있는 형태보다, 운영자가 바로 행동할 수 있는 문장으로 구성하는 것이 좋다.
- 2단계에서는 위험 이벤트 알림을 우선 구현하고, 이후 시스템 장애 알림은 모니터링/Alertmanager와 연계해 확장하는 것이 현실적이다.
- 요구사항 문서에는 위험 단계별 경보 발생 조건 설정, 경보 이력 관리, 조치 결과 기록, API 호출 상태 확인, 장애 인지 기능 등이 포함되어 있으므로,  
    알림 고도화는 단순 편의 기능이 아니라 운영 대응 체계의 핵심 기능으로 봐야 한다.
