작업 목적

실시간 센서 데이터 수집과 관제 화면 응답은 빠르게 유지하면서,  
상대적으로 시간이 걸리는 AI 분석, 이벤트 후처리, 이력 저장, 알람 전송 등의 작업은  
백그라운드에서 분리 처리할 수 있도록 **비동기 처리 구조를 구축하는 것**이 목적이다.

1단계에서는 데이터 수신과 즉시 표시가 핵심이었다면,  
2단계에서는 시스템이 실제 서비스 수준으로 확장되면서  
**“사용자 요청 응답”과 “시간이 걸리는 작업”을 분리**해야 한다.

즉, Django/FastAPI가 모든 작업을 한 번에 직접 처리하는 구조에서 벗어나,  
센서 데이터는 즉시 수신·저장하고,  
AI 추론 및 후속 작업은 Celery Worker가 별도로 처리하도록 설계한다.

---
작업 내용

1. 비동기 처리 대상 작업 정의
- 모든 작업을 Celery로 보내는 것이 아니라,  
    즉시 처리해야 하는 작업과 백그라운드로 넘겨도 되는 작업을 구분해야 한다.
- 비동기 처리 대상 예시:
    - AI 이상 탐지 요청
    - 예측 결과 저장
    - 이벤트 로그 후처리
    - 알람 이력 저장
    - 외부 알림 발송(Discord/Slack/이메일)
    - 장기 통계 집계
- 동기 처리 대상 예시:
    - 센서 데이터 수신
    - 현재 화면에 즉시 필요한 최신 상태 반환
    - 사용자 인증/권한 검증

2. 요청 응답과 후처리 분리
- 기존에는 센서 데이터가 들어오면 서버가 즉시
    - 저장
    - 임계치 판단
    - AI 분석
    - 알람 이벤트 생성
    - 응답 반환  
        순서로 모두 처리했을 수 있다.
- 2단계에서는 이 중 시간이 오래 걸리는 작업을 분리한다.
- 예:
    1. 센서 데이터 수신
    2. DB 저장
    3. 간단한 즉시 판단 수행
    4. Celery task 등록
    5. API는 빠르게 응답 반환
    6. Celery가 백그라운드에서 AI 분석 수행
- 이렇게 해야 API 응답이 지연되지 않는다.

3. Celery + Redis 기본 구조 구성
- Celery는 비동기 작업 실행기 역할을 한다.
- Redis는 Celery Broker로 사용하여 작업 큐를 중간에서 전달한다.
- 기본 구조는 다음과 같다.

```
Django / FastAPI  
   ↓ task 등록  
Redis (Broker)  
   ↓  
Celery Worker  
   ↓  
AI 분석 / 이벤트 후처리 / 알람 처리
```
이 구조를 통해 웹 서버와 작업 처리 서버의 책임을 분리할 수 있다.

4. AI 분석 작업을 Task로 분리
- 2단계 핵심은 AI 이상 탐지이므로,  
    ARIMA 분석 요청을 Celery task로 분리하는 것이 우선이다.
- 센서 데이터가 저장되면, 최근 시계열 데이터를 조회하여  
    AI 서버 분석 요청 또는 직접 모델 추론을 Celery task 내부에서 수행한다.
- 이렇게 하면 사용자는 API 응답을 기다리지 않고,  
    시스템은 뒤에서 분석을 마친 후 결과를 저장할 수 있다.

5. 이벤트 후처리 분리
- 임계치 초과, 지오펜스 진입, AI 이상 탐지 결과 등으로 생성된 이벤트는  
    추가적인 후처리가 필요할 수 있다.
- 예:
    - 이벤트 로그 저장
    - 중복 이벤트 병합
    - 이벤트 심각도 재분류
    - 통계 데이터 누적
- 이러한 후처리도 비동기 작업으로 분리하면 메인 API 부담을 줄일 수 있다.

6. 외부 알림 작업 분리
- Slack, Discord, 이메일 등 외부 알림 발송은 네트워크 지연이 발생할 수 있으므로  
    동기 처리하면 전체 응답 속도에 영향을 줄 수 있다.
- 따라서 알람 메시지 생성 후 실제 외부 전송은 Celery task로 넘기는 것이 적절하다.
- 1단계에서는 화면 UI 알람만으로 충분했지만,  
    2단계에서는 운영 환경 대응을 고려해 외부 채널 연동을 비동기화해야 한다.

7. 작업 상태 추적 구조 마련
- 비동기 작업은 즉시 결과가 나오지 않으므로  
    작업 상태를 추적할 수 있어야 한다.
- 예:
    - PENDING
    - STARTED
    - SUCCESS
    - FAILURE
- 특히 AI 분석 결과가 바로 화면에 반영되어야 한다면  
    작업 완료 후 DB 상태를 변경하거나, 상태 조회용 API를 둘 수 있다.
- 장기적으로는 WebSocket을 통해 “분석 완료” 이벤트를 프론트로 보낼 수도 있다.

8. 실패 처리 및 재시도 정책 정의
- Celery task는 네트워크 오류, AI 서버 오류, DB 저장 실패 등으로 실패할 수 있다.
- 따라서 다음 항목을 정의해야 한다.
    - 최대 재시도 횟수
    - 재시도 간격
    - 실패 시 로그 저장 방식
    - 실패 이벤트의 운영자 표시 여부
- 2단계에서는 성공 흐름뿐 아니라 실패 흐름도 설계 대상이다.

9. 우선순위 분리
- 모든 비동기 작업이 동일한 중요도를 가지는 것은 아니다.
- 예:
    - AI 분석: 중요
    - 통계 집계: 덜 중요
    - 외부 알림: 중요
- 향후 확장을 고려하면 큐를 분리하거나 우선순위를 설정할 수 있는 구조를 염두에 두는 것이 좋다.
- 2단계 초반에는 단일 큐로 시작해도 되지만,  
    작업 종류를 코드 레벨에서 분리해두면 확장에 유리하다.

10. 운영 관점의 비동기 구조 정리
- 비동기 처리를 도입하면 “응답은 빨라졌지만 실제 내부 작업은 늦게 끝나는” 구조가 된다.
- 따라서 운영자는 다음을 알 수 있어야 한다.
    - 현재 큐에 작업이 얼마나 쌓였는가
    - 어떤 작업이 실패했는가
    - AI 분석이 얼마나 오래 걸렸는가
- 이 때문에 Celery는 이후 Prometheus / Grafana 모니터링과 자연스럽게 연결된다.

세부 작업 순서

STEP 1. 비동기 대상 작업 목록 정리
- 현재 시스템 기능 중 어떤 작업이 Celery 대상인지 정의한다.
- 즉시 처리와 백그라운드 처리를 구분한다.

STEP 2. Celery 기본 설정 구성
- Django 프로젝트에 Celery를 연결하고, Redis Broker를 설정한다.
- Worker가 정상 실행되는지 확인한다.

STEP 3. 테스트용 단순 Task 작성
- 예: 문자열 출력, 더미 이벤트 저장
- Celery가 실제로 동작하는지 먼저 검증한다.

STEP 4. AI 분석 Task 분리
- 센서 데이터 저장 후 ARIMA 분석을 수행하는 task를 만든다.
- 이 task는 최근 시계열 조회 → 분석 → 결과 저장 순서로 동작하게 한다.

STEP 5. 이벤트 후처리 Task 분리
- 임계치 초과나 알람 발생 시 이력 저장, 통계 누적, 외부 알림 전송 등을 task로 분리한다.

STEP 6. API 응답 흐름 단순화
- 메인 API는 데이터 저장 및 최소 판단까지만 수행하고,  
    AI 분석 및 후처리는 task 등록 후 즉시 응답하도록 수정한다.

STEP 7. 상태 추적 로직 마련
- task 실행 결과를 DB 또는 상태 조회 API로 확인할 수 있게 한다.

STEP 8. 실패 및 재시도 정책 적용
- 예외 처리, retry, timeout 기준을 설정한다.

STEP 9. 성능 테스트
- Celery 적용 전후 API 응답 시간 차이를 비교한다.
- 작업이 백그라운드로 정상 넘어가는지 확인한다.

STEP 10. 운영 연결 준비
- 추후 Prometheus, Grafana, Kubernetes 환경에서 Celery 상태를 모니터링할 수 있도록 구조를 정리한다.

권장 처리 흐름

① 센서 데이터 수신  
② DB 저장  
③ 최소 임계치 판단  
④ Celery task 등록  
⑤ API는 빠르게 응답 반환  
⑥ Celery Worker가 AI 분석 수행  
⑦ 결과 저장  
⑧ 필요 시 외부 알림 및 UI 반영

---
예시 시나리오

기존 동기 처리 방식
```
센서 데이터 수신  
→ DB 저장  
→ AI 분석  
→ 결과 저장  
→ 알람 생성  
→ 응답 반환
```

문제:
- 응답 지연 발생
- AI 분석이 느리면 전체 API가 느려짐

#### 비동기 처리 방식
```
센서 데이터 수신  
→ DB 저장  
→ Celery task 등록  
→ 응답 반환  
  
(백그라운드)  
→ AI 분석  
→ 결과 저장  
→ 알람 생성
```

효과:
- API 응답 속도 개선
- 무거운 작업을 분리 가능

Task 예시 구조

AI 분석 Task
- 입력:
    - sensor_id
    - metric
    - 최근 데이터 조회 조건
- 처리:
    - 최근 시계열 조회
    - ARIMA 예측
    - anomaly 판정
    - 결과 저장
- 출력:
    - 분석 결과 DB 저장
    - 필요 시 알람 이벤트 생성

외부 알림 Task
- 입력:
    - alert_id
    - message
    - channel_type
- 처리:
    - Discord/Slack 전송
- 출력:
    - 발송 성공/실패 로그 저장

완료 기준

- Django/FastAPI에서 Celery task를 정상 등록할 수 있다.
- Redis Broker와 Celery Worker가 정상 동작한다.
- AI 분석 작업이 백그라운드에서 처리된다.
- 메인 API 응답 시간이 이전보다 빨라진다.
- AI 결과 및 후처리 결과가 정상적으로 DB에 저장된다.
- 외부 알림 또는 후처리 작업이 메인 응답을 막지 않는다.
- 작업 실패 시 재시도 또는 실패 로그가 남는다.
- 작업 상태를 추적할 수 있다.

작업 시 주의사항

- 모든 로직을 무조건 비동기로 빼면 오히려 시스템 흐름이 복잡해질 수 있으므로,  
    응답 지연을 유발하는 작업만 우선 분리해야 한다.
- 1단계 즉시 알람 UI와 달리, 2단계 AI 결과는 약간 늦게 도착할 수 있으므로  
    즉시 판단과 분석 완료 후 판단을 구분해야 한다.
- Celery task는 반드시 재실행 가능(idempotent)하게 설계하는 것이 좋다.
- AI 분석 실패가 전체 시스템 장애로 이어지지 않도록 분리해야 한다.
- Broker(Redis)와 Worker 상태가 불안정하면 데이터 유실이나 지연이 생길 수 있으므로  
    이후 모니터링과 함께 관리되어야 한다.
- 요구사항 문서상 AI 분석, 경보 및 대응 연계, 이력 관리, 로그 관리가 모두 포함되어 있으므로  
    비동기 처리는 단순 성능 최적화가 아니라 시스템 운영 구조를 분리하는 핵심 설계 요소에 해당한다.
