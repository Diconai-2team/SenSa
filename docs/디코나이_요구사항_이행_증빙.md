# SenSa — 디코나이 4차 요구사항 ↔ 이행 증빙서

> **이 문서가 증빙하는 것**
> 디코나이(중기청 R&D) 4차 프로젝트가 제시한 요구사항을, SenSa 팀이 *실제로 동작하는 코드*로 어떻게 이행했는지를 1:1로 추적한다.
> 모든 이행 주장은 추정이 아니라 **레포지토리의 실제 파일·함수 경로**로 증빙한다.
> 작성 기준: 커밋 이력과 무관하게 **현재 코드 동작 기준**.

## 1. 증빙 대상·범위

디코나이 4차의 한 줄 정의는 다음과 같다.

> "센서 + 위치 + AI를 결합하여 산업 현장의 위험을 실시간으로 감지·예측하는 지능형 관제 시스템 구축"
> (출처: `docs/4차(디코나이프로젝트)/디코나이 관제 플랫폼 중기청 R&D과제.md`)

4차는 3차와 달리 **"보이게"가 아니라 "제대로 돌아가게"** 를 목표로 했고, 그 차이는 디코나이 문서가 직접 표로 정의했다.

| 구분 | 3차 | 4차 (본 증빙 대상) |
|------|-----|--------------------|
| 목적 | UI + 흐름 | 운영 + 확장 |
| 데이터 | 가짜 | 실제 구조 |
| AI | 없음 | **있음** |
| 모니터링 | 없음 | **있음** |
| 인프라 | 로컬 | **Docker + K8s** |

따라서 이 문서가 증빙해야 할 핵심 4가지는:

1. **실시간 데이터가 실제로 흐르는가** (생성 → 수신 → 평가 → 방송 → 화면)
2. **AI 이상탐지가 단순 임계치를 넘어 동작하는가** (ARIMA + IsolationForest)
3. **운영 구조를 갖췄는가** (비동기·캐시·메시지 계층·모니터링)
4. **확장·복구 가능한 인프라인가** (Docker → Kubernetes / HPA)

## 2. 아키텍처 — 디코나이 요구 구조 vs SenSa 실제 구조

### 2-1. 디코나이가 제시한 기준 구조

```
[센서 데이터 생성/수집]
        ↓
[엣지 게이트웨이 (FastAPI)]
        ↓ (WebSocket / Stream)
[관제 서버 (Django + DRF)]
        ↓
[프론트 대시보드]
        ↓
[AI 분석 서버 (FastAPI)]
        ↓
[알람 시스템]
        ↓
[Prometheus → Grafana → Kubernetes]
```

### 2-2. SenSa가 실제로 구현한 구조

```
┌──────────────────────────┐
│ fastapi_generator         │  센서 생성기 (FastAPI, 1초 틱 scheduler)
│  scheduler.py / poster.py │  └ httpx 로 DRF 에 직접 POST (임시 큐 없음)
└─────────────┬────────────┘
              │ HTTP POST /devices/sensor-data/  (InternalAPIKey 인증)
              ▼
┌──────────────────────────────────────────────────────────┐
│ Django 관제 서버 (DRF, ASGI=daphne)                         │
│  devices/views.py  SensorDataView.post  ← 단일 수신 진입점   │
│    ├ 부하 게이트 _should_persist / _ai_due (Redis SET NX)    │
│    ├ AI: detect_anomaly() · predict_trend() · arima_forecast│
│    └ alerts/services/sensor_evaluator.evaluate_sensor       │ ← 판정·알람 단일 출처
│         ├ classifiers.py (임계치 정상/주의/위험)              │
│         ├ state_store.py (Redis 최신상태 캐시, graceful)     │
│         └ realtime/publishers.py (Channel Layer 발행)        │
└───────┬───────────────────────────────┬──────────────────┘
        │                               │
        ▼ Redis Channel Layer           ▼ Celery (Redis broker)
┌─────────────────────┐        ┌───────────────────────────┐
│ realtime/consumers  │        │ alerts/tasks.py            │
│ DashboardConsumer   │        │  send_external_notification│→ Discord/Slack
│ 1연결 → 4그룹 구독    │        │ geofence/tasks tick_zones  │  (notifiers.py)
│ (alarms/workers/    │        │ backoffice cleanup/backup  │
│  sensors/zones)     │        └───────────────────────────┘
└────────┬────────────┘
         ▼ WebSocket
   브라우저 대시보드 (지도·이벤트·가스·전력·AI성능)
         ▲
         │ 위험구역: geofence/diffusion.py (그레이엄 확산)
         │           polygon_utils.py (convex hull)
         │           zone_lifecycle.py (tier 승격)
         └──────────────────────────────────────────

[관측] Django:8000 / generator:8001 / celery:9809 → Prometheus → Grafana
       (sensa_observability/)
[배포] Docker Compose → Kubernetes (manifests/ : Deployment·Service·Ingress·HPA)
```

### 2-3. 핵심 차이 (의도된 설계 선택)

디코나이 기준 구조는 `FastAPI(센서) → Redis Stream/PubSub → Django` 였으나, SenSa는 **생성기가 DRF로 직접 POST**하고 **Redis는 방송·캐시·브로커·부하게이트**로 사용한다. 이유와 트레이드오프는 5절 참조. 이는 "판정·알람을 한 곳(`evaluate_sensor`)에서만 수행"하는 **단일 출처(single source of truth)** 원칙을 지키기 위한 선택이다.

### 4-B. 4차 작업영역 7개 — 완료기준 대비 이행

> 각 작업영역 문서(`1️⃣`~`7️⃣`)의 **완료 기준**을 그대로 가져와 이행 여부와 증빙을 붙였다.

#### 1️⃣ AI 이상 탐지

| 디코나이 완료기준 | 이행 | 증빙 |
|-------------------|------|------|
| 센서 시계열 데이터 누적 저장 | ✅ | `devices/models.py` SensorData, 복합인덱스 `(device, -timestamp)` |

## 5. 솔직한 이행 차이·설계 선택

> 발표 템플릿의 "솔직한 한계" 슬라이드(10장)와 일관되게, 요구안과 다르게 간 부분을 명시한다. 이는 누락이 아니라 **의도된 설계 판단**이다.

**5-1. 수집 경로: Redis Pub/Sub 대신 DRF 직접 POST**
디코나이 기준 구조는 `생성기 → Redis(sensor.raw) → Django subscribe`였다. SenSa는 생성기가 `httpx`로 DRF에 직접 POST한다(`fastapi_generator/poster.py`). 이유: 판정·알람을 **한 곳(`evaluate_sensor`)에서만** 수행하는 단일 출처 원칙을 지키기 위함. 중간 PubSub 수집을 두면 발행 지점이 분산돼 중복 알람·정합성 문제가 생긴다. 대신 순간 폭주는 `_should_persist`/`_ai_due` 부하 게이트(Redis SET NX, 5초 창)로 흡수한다. (`devices/views.py:35,51`)

**5-2. AI 추론: Celery 오프로드 대신 인라인 + 게이트**
디코나이는 "AI 분석을 Celery task로 분리"를 권장했다. SenSa는 ARIMA/IF 추론을 DRF 요청 내에서 수행하되 device별 5초 창당 1회만 실행(`_ai_due`)하고, 모델 재학습만 비동기(`_maybe_refit`)로 처리한다. 이유: 경량 모델(ARIMA(1,1,0)/IsolationForest)이라 인라인 지연이 작고, Celery 왕복이 오히려 "화면 반영 지연"을 키운다. Celery는 **외부 알림·zone tick·정리/백업** 등 진짜 무거운/지연 허용 작업에 사용한다.

**5-3. 라이브러리 부재 graceful fallback**
statsmodels/sklearn 미설치 시 AI가 죽지 않고 선형 추세로 degrade한다(`arima_forecast.ARIMA_AVAILABLE`, `trend_predictor` fallback).

**5-4. 데모 범위 단순화 (템플릿 10장 기재 사항)**
단일 Redis/PostgreSQL = SPOF(데모 단순화), 앞단 별도 Nginx 없이 ingress-nginx → daphne 직접.
